# Consequences for EFFECT — design input only

The fixed-flow target has an immediate algebraic influence **once selected and evaluated**: FTC computes temperature error and prepares temperature-related requests. The recovered lookup itself does not accumulate deficit. The entire native loop may still be history-dependent through another controller and FTC state/timers. There is no basis yet for adding a second degree-minute integrator or claiming an absolute kW command.

A useful future controller should distinguish startup/capture/hold using observed compressor activity, actual/targetHz and limiting state where obtainable. Preserve requested target separately from accepted/effective target and keep command acknowledgments separate from physical response. An unchanged byte at a0.5C serializer boundary is not a new demand event; however other representations may retain more precision. Do not prescribe a minimum command interval from that quantization alone.

No native update/observation interval in seconds has been established. Current EFFECT's30s decision period,60s maximum measurement age, short/slow60/180s windows and startup settling are **Procon policy**, not Mitsubishi constants. Faster polling can return the same generation. Use source generation/age to measure response; avoid integrating another adjustment while the earlier request's acceptance/response is unresolved. A60s-old value may support holding a bounded command but is poor evidence for a fast trend; distinguish degraded feedback from proven native failure.

Rising measured flow toward its selected target plus falling/limitedHz is a useful *hypothesis* for impending normal stop, not a proven threshold detector. B2700's+2C branch cannot yet be used as a universal thermostat boundary. Native minimum capacity, flow limits, DHW priority or another-controller protection can explain reduced output despite positive error. In that situation increasing target blindly is not justified. Respect the user's measured40C ceiling and commanded55C ceiling as separate external constraints; P87 changes neither.

At6kW and15L/min, an assumed water heat balance gives delta5.74C. Rising return therefore raises required **measured** flow for the same thermal output. That balance says nothing by itself about how far above it the commanded target should be. If the allowable measured-flow ceiling prevents6kW, the achievable heat output must be reported rather than reinterpreting target55C as permission for actual55C.

Existing telemetry: flow, return, water flow, calculated thermalW, actualHz, target readback, operating phase, heater flags, pump run/level and brine temperatures. Needed for discrimination: outbound effective target/error/operation request, service17 targetHz and52 limit state with source timestamps, and phase/profile eligibility. Local RAM locations in this report are **not qualified external diagnostic addresses**, especially on21.00. A separate reviewed diagnostic feature or source-board capture is required.

Historical down/up data contradicts a simple instantaneous Hz=f(error) account: at a constant32.5C target Hz progressed38→40→42→44, with varying flow temperature and elapsed time. It does not isolate integration from time qualification, ramp limits or source-board constraints. The old command path could transition through curve mode when changing targets; it therefore cannot prove that the later direct-target firmware necessarily causes the same stop. Production effect.c/effect_feedback.c/control.c are unchanged.
