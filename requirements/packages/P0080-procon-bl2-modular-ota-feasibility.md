# P0080 — Feasibility: BL2, modular firmware and OTA

## Status
**Design/investigation/offline prototypes only.** No live flash writes, DIP changes or physical control. Codex must answer whether implementation is actually feasible with the source, documentation, tools and capabilities available. Every claim gets evidence or **UNKNOWN**, with an explicit blocker and required next experiment. This is not an implementation order for production OTA.

## Target design to investigate
STM32L433 Procon with vendor bootloader preserved at presumed 0x08000000–0x08007FFF; custom software starts at 0x08008000. Confirm boundaries rather than assuming them.
- **BL2 8 KiB**, resident: boot/hardware, RS485 at 9600 Modbus and 115200 OTA, CN105/A3 services, LED, time, baseline telemetry cache, flash OTA, minimal first-stage command router. Addressed Modbus system command values 0xFF OTA_ENTER and 0xFE OTA_WAIT; other commands routed to dispatcher.
- **Dispatcher 4 KiB**: non-system commands and feature routing, ABI/compatibility.
- **2 KiB per feature**: drifttelemetri (compressor Hz, supply/return, flow, heating W etc.); servicetelemetri (A3 codes, brine etc.); mode-kommandon (AUTO/EFFECT/VV); debug-kommandon (deliberate RAW testing); debug-telemetri (low-level diagnostics).
- A typical feature update sends dispatcher plus one feature (4+2 KiB), each split into transport packets no larger than Shelly's reported **240-byte limit including overhead**. Sizes are a target, not a conclusion. Confirm STM32 erase/page geometry and align slots accordingly.
- Existing original bootloader and physical DIP method remain the manual recovery mechanism. No automatic rollback/A-B requirement. An interrupted update must not boot inconsistent dispatcher/features; reattempt via surviving BL2 when possible, otherwise DIP recovery.
- Two Procons on one RS485: normal Modbus unique addresses at 9600; Shelly pauses schedules, verifies native AUTO before OTA, commands non-target to WAIT (silent RS485 output), commands target to OTA, switches link to **115200 addressless**, transfers image, then returns to 9600. Non-target reboot or exit from WAIT during transfer may cause failure and manual recovery; accepted risk, not a reason to add persistent WAIT. WAIT must not stop heat pump's native FTC operation.
- Deterministic reset-to-FTC-curve and ordinary DHW authorization is desired but not yet proven. Do not assume it makes EEPROM unnecessary until command/readback validation.

## Fundamental feasibility questions — answer ALL
1. **Knowledge and capability audit:** Does Codex have actual standalone source, linker/startup, toolchain, STM32L433 datasheet and reference manual, Procon board signals, Shelly raw UART abilities and test harness? For each component classify VERIFIED / INFERRED / UNKNOWN / BLOCKED, cite source, name what research or operator-provided physical evidence is missing. Differentiate an offline demo from proven hardware operation.
2. **Flash programming:** Can a running STM32L433 application program and erase its own designated flash pages using the MCU's documented FLASH registers/HAL? Analyze unlock/lock, erase units, write granularity, RAM/flash execution, interrupts, vector table, page and bank arrangement, write protection, RDP/PCROP, power loss, and isolation of BL2 and original bootloader. Explicitly answer **whether reversing the vendor bootloader is necessary** for BL2 flash writes; distinguish MCU-level self-programming from vendor 115200 updater protocol. Never propose changing protection bits as a shortcut.
3. **Boot chain:** Can vendor bootloader jump to a BL2 vector at 0x08008000, and can BL2 safely run dispatcher/features with MSP, VTOR and interrupt ownership? Confirm any vendor-image constraints and original DIP recovery pathway from available evidence. If bootloader behavior is unknown, propose the smallest separate test.
4. **Real code size and memory:** Compile the current real firmware, derive component map, linker sections, .text/.rodata/.data/.bss, flash and SRAM budgets, stack/heap, and platform ABI size. Create **offline** candidate BL2 8 KiB / dispatcher 4 KiB / five 2 KiB slots (with realistic implemented functionality or explicit stubs marked as such). Supply GNU map, size, reproducible compiler flags (-Os, LTO and comparison), margins and measured reasons any block overflows. Do not infer fit from reported 16 KiB monolith alone.
5. **Independent updatability:** Prove with two offline builds that modifying one 2 KiB feature does NOT move code/addresses for other slots. Evaluate fixed slot link scripts, BL2 ABI function table, versioning, callback registration, shared data, interrupts, relocation costs, flash page alignment and manifest compatibility. Verify dispatcher + feature interrupted midway cannot be treated as a valid application. Compare a larger-slot or full-image delta alternative if 8/4/2 fails.
6. **8 KiB BL2 reality:** Can CN105/A3, RS485/Modbus, LED, scheduler/timer, essential polling/cache, the first-stage router, native AUTO restoration, 115200 uploader, image checks and self-programming fit **simultaneously**? If some capabilities are not presently implementable, name them; no optimistic partial build passed as a full fit.
7. **Shared bus:** Verify two addresses, RS485 DE/tristate and exclusive master, Shelly ability to switch 9600 to 115200 and transport binary chunks of at most 240 total bytes, WAIT ACK before OTA_ENTER, target-only listener, timeout/reset paths. Do not assume actual bus silence or correct baud switching without evidence.
8. **Update and retry behavior:** Define a simple bounded addressless BL2 upload protocol with offset, length, checksum, full-image/slot validation, version/target compatibility, completion and retry status. Distinguish BL2 protocol from vendor commands already studied in P0075; do not redo prior host-uploader reverse engineering unless a specific gap necessitates it. Test torn pages, invalid images, target reset, non-target leaving WAIT, mismatched image, interrupted Shelly upload and reattempt. Do not add unnecessary A/B or EEPROM recovery.
9. **L2 functionality:** Decide ownership of telemetry and mode interfaces and what remains readable if dispatcher or one feature is invalid. Preserve deliberate RAW test access, no parallel-agent governance. Document that CN105 commands for heating/DHW inhibit, native AUTO restoration and reset behavior still require verification.

## Required method
Follow G2 bootstrap. Inspect P0072 r3, P0075, P0076, P0079, actual portable firmware code and existing updater research. Hardware is **STM32L433**, not the old MC9S12. Stage A: audit references and blockers. Stage B: compile map/size and modular ABI offline spike. Stage C: flash self-programming feasibility from STM32 docs + mock-backed test (not hardware proof). Stage D: dual-device OTA handover design and failure tests. Stage E: GO / CONDITIONAL GO / NO-GO decision, with recommended alternate budgets if required.
