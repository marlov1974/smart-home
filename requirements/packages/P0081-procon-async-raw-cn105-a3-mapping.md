# P0081 — Asynchronous RAW GET and CN105/A3 command mapping

## Authorization and intent
Ordered engineering package for Codex: design, implement and offline-test a reusable asynchronous Modbus diagnostic interface in portable Procon firmware, plus a Mac-side mapping utility. **Automated discovery is READ-ONLY.** No unsupervised live scanning, active SET, control mode changes, bootloader operations, flash/EEPROM access or real pump actuation. Actual live execution requires an explicit operator handoff, agreed bounded scan set and observation window. No broad unsolicited experiments on a running heating system.

## Logical command model
Use the user-agreed symbolic commands **0xFD = submit RAW GET** and **0xFC = retrieve result/status**. These are *application-level opcodes carried within standard addressed Modbus*, NOT Modbus function codes or unframed RS485 bytes.
- Write request through FC16 to a **new, versioned and isolated** holding-register range; never reinterpret P0072 r3's existing FC16 control block at offset 300/count 8.
- Fetch snapshot through FC04 from a new input-register range. Modbus FC04 is naturally read-only; the logical 0xFC is an explicit request/result selector or documented API identity, not a second physical write requirement. Detail exact register map and on-wire bytes and test on existing Shelly Modbus client.
- Request schema: API version, opcode 0xFD, monotonically increasing request_id/sequence, request kind DIRECT_GET or SERVICE_A3, direct 8-bit GET code (e.g. 0x07,0xA1,0xA2), service request number (e.g. 27,28), bounded optional parameter bytes ONLY where format verified, flags reserved zero, command CRC/validation as needed. **No arbitrary CN105 frame injection; GET 0x42 only**, except the already established *read-only* multi-step A3 operation. No permission to fuzz unknown control payloads.
- Status schema (logical 0xFC): echo request_id, kind, code, status IDLE/QUEUED/BUSY/DONE/TIMEOUT/UNSUPPORTED/BAD_RESPONSE/ERROR, payload length, raw reply, transport/protocol error, validity flag, completion generation and age/time; raw bytes preserved exactly. Make terminal outcomes sticky until next accepted request or explicit read-safe reset. DONE only for a correlated complete valid response. Never treat stale previous data as this request's result.
- Immediate FC16 ACK means **request accepted**, NOT FTC answered. At most one pending physical CN105 request per Procon initially; reject BUSY or sequence conflict deterministically, do not silently overwrite. Repeated same request_id is idempotent, not a second physical query. Bound queue, retries, timeouts, latency and RAM. Direct queries and exclusive A3 operations must use the existing CN105 arbiter; no interleaving inside A3. Continue essential telemetry if scheduling permits; expose scan-induced gaps. Request cancellation/expiration must be explicit.
- Show the literal user workflow: 0xFD A3 0x001B starts service code 27; seconds later 0xFC polling gets BUSY then DONE plus raw response. Also 0xFD DIRECT 0x07 / 0xA1 / 0xA2. Include actual Modbus FC16/FC04 examples with register addresses and request IDs.

## Mac-side mapping utility
Produce a reusable Python CLI, portable scripts/tests, machine-readable evidence and human-readable comparison report. Script interacts through current Shelly/RS485 Modbus interface using supported client functions, not direct CN105 UART access.
- **DIRECT discovery**: enumerate 0x00–0xFF GET codes (only in an explicitly approved live run; offline mock fixtures by default). Construct known safe zero-payload GET framing only where established, record raw correlated replies, status/timeout, payload sizes, repeatability, decoding and latency. A no-reply code remains UNKNOWN/NO_RESPONSE, not automatically invalid. Check protocol capabilities/firmware variants. Distinguish direct `GET 0xA3` from parameterized A3 service reads.
- **A3 discovery**: separately enumerate the **documented service/request-code list from uploaded Geodan SER manual**, including valid noncontiguous three-digit codes; prioritize 17,18,19,25,26,27,28,52 and FTC counterparts, not merely 0–255. Do not call every 0–999 code by default or invent semantics for undocumented IDs. Optional extended candidate ranges require a second operator-approved scope. Respect the empirically established multi-step service transaction and scheduling, with bounded retries/delays. Record code-to-reply data, service success/failure/status, length, signedness candidate, source quality, and repeatability.
- Per reading preserve: device identity, FTC/software/board revision where available, kind/code, request_id, timestamps, raw TX intent and raw RX bytes as exposed, full response length, checksum validity, status, timeouts/retries, freshness, value hypotheses, matching documented display code/units/scale and provenance (manual vs public reference vs physical measured). Store JSONL and CSV summary; optional human-readable Markdown report with confirmed/unconfirmed/unsupported classifications.
- Take **at least two separated reads per code** when possible, and optional before/after safe operating-condition observations only by operator choice. Never infer a field's meaning solely from a plausible number or 1 matching sample; label unknown bytes. Follow known service 27/28 evidence; absence of reply does not prove unsupported. Separate ordinary A3 from fixed standard GET by wire-protocol level.
- Rate limits: configurable inter-request delay, bounded per-operation timeout/retries, max-total-runtime and resumable checkpoint; default conservative; provide dry-run plan and operator-visible stop/cancel; block any scan if an active L2 EFFECT/VV mission or autonomous test is running. Do not require concurrent 'agent' authorization: operator intentionally pauses the weekly schedule before active experiments.
- End-to-end never sends SET 0x41, 0x5A vendor bootloader, writable Modbus control commands other than the precisely bounded diagnostic FC16 submit, or experimental write parameters. Dangerous service codes such as resets/initializations may occur in display request-code lists: mark them **excluded from scan** until proved purely read-only. Request-code enumeration is not automatically safe merely because the transport uses 0x42.
- Never change heating curves, heating/DHW permission, FTC service settings or reset faults during mapping. Raw GET may still burden CN105 or elicit uncommon device behavior: live runs remain supervised, staged, and abort on faults, unexpected latency or quality degradation.

## Architecture ownership and portability
Fit the emerging P0080 BL2/dispatcher/debug-command/debug-telemetry split without assuming its partition sizes are proven. Reuse existing P0072 r3 Modbus, CN105, A3 exclusive arbiter, 20 telemetry fields, readback/lease behaviors; preserve production data/control compatibility. Make mapping utility usable before final BL2 refactoring if feasible. Offline test against mocked Procon response variants.

## Acceptance gates
1. ABI/register map defined; no conflict with existing offsets including FC16/300; no interpretation of 0xFC/0xFD as raw Modbus function codes.
2. FC16 submit accepted; FC04 reports BUSY then DONE and raw bytes with matching request_id. Timeout, CRC-invalid, unsupported, incomplete A3, wrong ID, stale result and disconnect are distinguishable.
3. CN105 single transaction ownership preserved under simultaneous background FAST/A3 diagnostics. Bounded resources; zero-parameter direct read validated; A3 uses true existing multi-stage sequence.
4. Offline enumeration tests cover direct 256 codes, manual allowlisted service codes incl codes above 255, hazard exclusions, resumable partial scan, no-response, duplicate, change between samples, abort, dry-run and report formatting. No arbitrary SET emitted by script, mock or physical code.
5. Reports explicitly differentiate protocol response, source identity, interpretation certainty and hardware validation. Unknown isn't guessed as zero or 'no feature'.
6. Document minimum approved live test: isolated one-unit identification, operator confirmation, inactive schedules and no EFFECT, conservative initial subset (0x07,0xA1,0xA2,A3/27,A3/28), then staged wider scans if operator approves.
7. Any platform size impact is measured and passed to P0080 feasibility; do not silently exceed 8/4/2 KiB design targets.
